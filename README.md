# DSpace Reporting

This project produces DSpace reports from Jupyter notebooks and a YAML configuration file.

The current workflow can run DB, Solr and Matomo metric notebooks for either a single month or a sequence of complete months. The current month is excluded automatically in order to avoid partial metrics.

## Structure

```text
config/
  settings.example.yaml   # example configuration
  settings.local.yaml     # actual local configuration
notebooks/
  01_db_metrics.ipynb     # PostgreSQL metrics
  02_solr_metrics.ipynb   # Solr metrics
  03_matomo_metrics.ipynb # Matomo metrics
src/
  dspace_reporting/
    config.py             # config loading and normalization
    periods.py            # month/range resolution
    export.py             # export directory helpers
    runners/
      run_notebook_periods.py
exports/
  db/
    monthly/              # metrics related to the reference_month
    always/               # overall-state metrics
  solr/
  matomo/
reports/
  metrics_catalog.md      # metric taxonomy and analysis areas
  index.html              # browsable archive of generated monthly reports
  assets/                 # static assets published with the report site
  monthly/                # static reports generated by month
  always/                 # overall-state reports for always snapshots
assets/
  branding/               # institutional logo used in reports and future dashboard
 data/
tests/
```

## Setup

Create the virtual environment in the project root:

```powershell
python -m venv virtual_env
```

Activate it:

```powershell
.\virtual_env\Scripts\Activate.ps1
```

Install dependencies in the Python/Jupyter environment that will run the notebooks:

```bash
pip install -r requirements.txt
```

Then install the project in editable mode so Python can find the `dspace_reporting` package without setting `PYTHONPATH`:

```powershell
python -m pip install --no-use-pep517 -e .
```

## Configuration

The main configuration file is:

```text
config/settings.local.yaml
```

The most important section is `run`:

```yaml
run:
  mode: "monthly"
  reference_month: "current"
  always_reference_month: null
  start: "2026"
  end: null
  create_month_subfolders: true
  export_outputs: true
  overwrite_exports: false
  overwrite_reports: false
  include_snapshot_metrics: true
  future_start_policy: "current_year"
```

### Main fields

`mode`

- `single`: runs only `reference_month`.
- `monthly`: computes all complete months from `start` to `end`.

`reference_month`

A single month in `YYYY-MM` format, or `"current"` / `"today"` to use the month of the execution date. It is kept for notebook compatibility and for `mode: single`.

`always_reference_month`

Optional label for `always` exports. If set to `"current"`, the runner uses the current month on the execution date. If it is `null` or missing, the runner uses `reference_month`; if `reference_month` is also missing, it still falls back to the current month.

`start`

Initial period. Accepted values include:

```yaml
start: "2026"
```

which means January 2026, or:

```yaml
start: "2026-03"
```

which means March 2026.

`end`

Final period. Accepts `YYYY-MM` or `null`.

With:

```yaml
end: null
```

the program automatically uses the month preceding the current month.

Example: if the script is launched on May 11, 2026, the last included month is `2026-04`.

`overwrite_exports`

If `false`, the runner checks the expected exports before executing each period. In `monthly` mode, it skips periods that already have all CSV files, runs missing ones, and stops only when it finds a partially exported period.

`overwrite_reports`

Follows the same operational logic as `overwrite_exports`, but for HTML reports:

- if `false`, the report runner skips monthly or `always` reports that already exist;
- if `true`, it regenerates reports even when `report.html` already exists.

`export_outputs`

If `false`, the notebook runs the analyses and displays results on screen, but does not write CSV files. The same behavior can be enabled from the command line with `--display-only`, without editing the YAML file.

`future_start_policy`

If `start` is in the future:

- `current_year`: restart from January of the current year.
- `error`: stop execution with an error.

### Matomo

The `matomo` section contains the endpoint, site id, token and domain filter used by page-URL metrics:

```yaml
matomo:
  base_url: "https://stats.ilc.cnr.it/"
  site_id: 12
  token_auth: "CHANGE_ME"
  token_description: "jupyter-notebook-analytics"
  domain_filter: "dspace-clarin-it.ilc.cnr.it"
  verify_ssl: true
```

`domain_filter` is read by `03_matomo_metrics.ipynb` and limits page-view classifications to URLs belonging to the configured DSpace domain.

```yaml
run:
  mode: "monthly"
  start: "2026"
  end: null
```

```text
2026-01
2026-02
2026-03
2026-04
```

```yaml
run:
  mode: "monthly"

  end: "2026-03"
```

```text
2025-09

2025-11
2025-12

2026-02
2026-03
```

```yaml
run:
  mode: "single"
```

## Preview What Will Run

Before launching the analyses, use the dry run:

```powershell
python -m dspace_reporting.runners.run_notebook_periods --dry-run
```

Expected output:

```text
Months to process: 2026-01, 2026-02, 2026-03, 2026-04
```

The dry run does not open database connections and does not execute the notebook.

To preview execution for a single month without editing the YAML file:

```powershell
python -m dspace_reporting.runners.run_notebook_periods --month 2026-05 --dry-run
```

## Run the Reporting Notebooks

To run all available reporting notebooks for all months resolved from the configuration:

> [!WARNING]
> If the configured services (PostgreSQL, Solr, Matomo or the SSH bastion) are located
> on a private network, make sure you are connected to the VPN before running the reports;
> otherwise the runner may not be able to reach them.

```powershell
python -m dspace_reporting.runners.run_notebook_periods
```

To limit execution to one or more specific months from the command line:

```powershell
python -m dspace_reporting.runners.run_notebook_periods --month 2026-05
```

or:

```powershell
python -m dspace_reporting.runners.run_notebook_periods --month 2026-04 2026-05
```

The `--month` option overrides month resolution from the YAML `run` section. If the notebooks contain cells tagged `always`, those cells are still executed only once according to the `always_reference_month` logic described below.

The runner checks expected exports by source. If DB exports are already present but Solr or Matomo exports are missing, it skips DB and generates only the missing exports.

To run the same analyses without writing CSV files:

```powershell
python -m dspace_reporting.runners.run_notebook_periods --display-only
```

In this mode, the runner prints section titles, textual cell outputs and textual representations of tables produced with `display(...)` to the console.

The runner:

1. reads `config/settings.local.yaml`;
2. resolves the months to process;
3. creates a temporary configuration for each month;
4. passes that configuration to the notebook through the `DSPACE_REPORTING_CONFIG` environment variable;
5. executes cells tagged `monthly` once per month;
6. executes cells tagged `always` only once.

The local configuration file is not modified on each pass.

## Use a Different Configuration File

You can pass a different YAML file:

```powershell
python -m dspace_reporting.runners.run_notebook_periods --config config/settings.local.yaml
```

## Run a Single Notebook

The runner also accepts a specific notebook:

```powershell
python -m dspace_reporting.runners.run_notebook_periods --notebook notebooks/02_solr_metrics.ipynb --dry-run
```

To execute it for real:

```powershell
python -m dspace_reporting.runners.run_notebook_periods --notebook notebooks/02_solr_metrics.ipynb
```

Note: to work correctly, the notebook must read its configuration from `DSPACE_REPORTING_CONFIG`, as the notebooks included in this project do.

## Exports

Exports are separated first by source and then by metric scope:

```text
exports/db/monthly/2026-04/
exports/db/always/2026-04/
exports/solr/monthly/2026-04/
exports/solr/always/2026-04/
exports/matomo/monthly/2026-04/
exports/matomo/always/2026-04/
```

`monthly` contains analyses related to the month or to time windows computed from `reference_month`, such as uploads in the month or users active during the last 12 months.

`always` contains analyses about the overall state of the source at execution time, such as total items, communities, collections, groups, licenses or structural anomalies.

If `overwrite_exports: false`, the runner skips already complete periods, executes periods without CSV files, and stops when it finds a partially exported period. To rerun an already complete period, delete or move the existing CSV files, or temporarily set `overwrite_exports: true`.

## Monthly and Always Execution

Notebooks with cells tagged `monthly` and `always` are executed while keeping monthly metrics separate from overall metrics:

- `exports/db/monthly/<reference_month>/` for monthly metrics;
- `exports/db/always/<reference_month>/` for overall metrics;
- `exports/matomo/monthly/<reference_month>/` for monthly Matomo metrics;
- `exports/matomo/always/<reference_month>/` for overall Matomo metrics.

`monthly` cells are executed for every selected month. `always` cells are executed only once, using `run.always_reference_month` when present, otherwise `run.reference_month`, otherwise the current month on the execution date.

Monthly queries must use `REPORT_MONTH_DATE` and `REPORT_AS_OF_DATE`, not `CURRENT_DATE`, whenever the metric depends on the selected period.

## Static Reports and Dashboard

The recommended next-stage architecture separates three layers:

1. notebooks produce CSV files in `exports/`;
2. reporting scripts read the exports and generate final outputs in `reports/`;
3. a future dashboard will explore historical exports and make existing reports browsable without duplicating metric-calculation logic.

This separation intentionally keeps:

- `exports/` for CSV files only, split by source, scope and period;
- `reports/` for final products only: HTML pages, images, metadata and possible future PDFs.

This provides:

- archivable and shareable monthly reports;
- images saved during report generation;
- future interactive exploration of historical data.

The catalog of planned metrics and analytical sections is available in:

```text
reports/metrics_catalog.md
```

### Institutional Branding

To include the institutional logo in reports and, later, in the dashboard:

1. create the folder:

```text
assets/branding/
```

2. save the logo inside it, for example:

```text
assets/branding/logo.png
```

3. configure the path in `config/settings.local.yaml`:

```yaml
reporting:
  institution_name: "ILC4CLARIN"
  institution_subtitle: "DSpace monthly institutional report"
  archive_title: "Monthly report archive"
  logo_path: "assets/branding/logo.png"
```

Supported formats:

- `SVG`, preferred format;
- `PNG`, recommended for raster images with transparent background;
- `JPG` / `JPEG`, accepted as fallback.

Recommendations for raster files:

- recommended minimum width: `300 px`;
- ideal width: `600-1200 px`;
- recommended maximum size: `2 MB`;
- prefer a horizontal logo, roughly with an aspect ratio between `2:1` and `5:1`.

### Generate Static Reports

First install the updated dependencies:

```powershell
python -m pip install -r requirements.txt
```

Then generate reports for all months resolved from the `run` configuration, following the same general logic used for exports:

```powershell
python -m dspace_reporting.runners.build_reports
```

To preview what would be generated without writing files:

```powershell
python -m dspace_reporting.runners.build_reports --dry-run
```

To generate one or more explicit months:

```powershell
python -m dspace_reporting.runners.build_reports --month 2026-04
```

or:

```powershell
python -m dspace_reporting.runners.build_reports --month 2026-03 2026-04
```

To regenerate an existing report without editing the YAML file:

```powershell
python -m dspace_reporting.runners.build_reports --month 2026-04 --overwrite-reports
```

For each month, the report generator creates:

- `report.html`, an institutional report readable in a browser;
- `manifest.json`, with metadata about the generated report;
- images in `figures/`, reusable outside the dashboard as well.

The source logo file remains configured under `assets/branding/`, but during generation it is copied to `reports/assets/branding/`. Report HTML files reference the published copy under `reports/`, so the entire reports folder can be served or copied as a standalone static site.

### Publish Reports on a Web Server

To publish the static site, it is enough to serve the contents of:

```text
reports/
```

The folder contains:

- `index.html`, the entry page;
- `monthly/` and `always/`, with generated HTML reports;
- `assets/`, with shared static assets used by the site;
- `figures/` inside individual monthly reports, with local charts.

This allows the site to be served directly by Apache without depending on paths outside the document root for logos or generated images.

Note: Bootstrap is currently loaded from a CDN. If a fully offline deployment is required, copy Bootstrap under `reports/assets/` as well and reference it locally from the HTML files.

Each run also updates `reports/index.html`, which acts as a browsable archive of already generated monthly reports. Each report also includes links to the previous month, next month and general archive. Previous/next links are computed only from HTML reports that already exist or are generated in the current build, so they do not point to months for which no page is available yet. The title shown on the archive page and in the HTML `<title>` tag is read from `reporting.archive_title` in the configuration file.

The monthly HTML report includes:

- a general summary with main KPIs;
- a monthly trend chart;
- a view of the most active collections;
- a view of the geographic origin of visits;
- a view of the most consulted page types;
- a section on the overall repository profile based on `always` metrics;
- a content-usage section, with top items and download distribution;
- a traffic-acquisition section;
- a quality-and-compliance summary based on the latest available `always` snapshot;
- short explanatory texts and a methodological note.

HTML report sections are expandable/collapsible. The `always` report, which contains more technical and administrative sections, also uses a horizontally scrollable `navtab` bar: each tab shows one section at a time and makes navigation easier as the number of blocks grows.

If a monthly report already exists and `run.overwrite_reports` is `false`, the runner skips it. To regenerate it, temporarily set `run.overwrite_reports: true`, use `--overwrite-reports`, or move/delete the month folder.

This is a first institutional baseline: the reporting engine is separated into reusable modules under `src/dspace_reporting/reporting/`, so a future dashboard can reuse the same logic without changing the role of `exports/` and `reports/`.

### `always` Metrics in Reports

`always` exports remain stored separately under:

```text
exports/<source>/always/<reference_month>/
```

The reporting layer also generates a separate family of reports:

```text
reports/always/<reference_month>/
```

`always` metrics are therefore used in two ways:

- as state snapshots embedded in monthly reports, to contextualize the month;
- as standalone overall-state repository reports under `reports/always/`.

The standalone `always` report includes dedicated sections for:

- repository organization;
- item status and metadata quality;
- OAI exposure and Solr indexing;
- historical repository usage;
- accesses, referrers and Matomo traffic;
- geography, devices and technology;
- users, groups, workflow and technical integrity.
